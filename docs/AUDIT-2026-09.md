## Synthèse — les 3 choses qui bloquent vraiment le cap

1. **Pas de notion d'utilisateur, et la persistance perd des données sous
   concurrence.** `GET /conversations` renvoie tous les fils de tous les visiteurs, et
   deux tours simultanés sur un même fil n'en laissent qu'un sur disque (mesuré :
   2 messages au lieu de 4). C'est la couche de persistance qu'il faut reprendre, pas
   seulement une authentification à ajouter. → §2
2. **Le SQL généré peut lire n'importe quel fichier de l'hôte** : vérifié,
   `SELECT * FROM read_csv_auto('/etc/passwd')` passe le garde-fou lecture seule, dans
   le process de l'API et non dans la sandbox. Maxizoo aggrave l'exposition. → §6.1
3. **La mémoire grandit sans plafond et déborde en silence** : mesuré, 134 000 tokens
   envoyés, 32 767 évalués, aucune erreur, réponse absurde ; et elle vit dans `/tmp`,
   purgé à 10 jours. → §3

Changer de moteur d'inférence n'est, à l'inverse, pas un chantier lourd côté code
(une ligne dans `llm.py`) : le vrai risque y est le *tool calling*. → §4

## 1. Architecture

### 1.1 Composants et flux d'une requête

Ce que le code fait réellement, pour un `POST /chat` :

1. **`api/app.py`** — `chat()` ([api/app.py:66](../src/data_analyst_agent/api/app.py#L66))
   charge (ou crée) la conversation, appelle l'orchestrateur, puis écrit le tour dans
   `transcript.json`. L'orchestrateur est construit **paresseusement** et gardé dans
   `app.state.orchestrator` ([api/app.py:47-57](../src/data_analyst_agent/api/app.py#L47)).
2. **`Orchestrator.ask()`** ([orchestrator/graph.py:138](../src/data_analyst_agent/orchestrator/graph.py#L138))
   instancie un `ConversationWorkspace` (lecture du manifeste et du contexte sur
   disque), invoque le graphe, puis mémorise le tour.
3. **Nœud `plan`** ([graph.py:353](../src/data_analyst_agent/orchestrator/graph.py#L353))
   — 1 appel LLM à sortie structurée `Plan`.
4. **Routage `_route`** ([graph.py:224](../src/data_analyst_agent/orchestrator/graph.py#L224))
   — du code, pas du prompt : conforme au principe annoncé (ARCHITECTURE §1).
5. **Une capacité** : `retrieval` (agent SQL à tools, jusqu'à
   `retrieval_request_limit = 10` allers-retours), `analysis` (génération de code +
   sandbox, jusqu'à `analysis_max_attempts = 3`), `inference` (déterministe, sans
   LLM), `fetch_predict` (SQL puis predict).
6. **Nœud `synthesize`** ([graph.py:675](../src/data_analyst_agent/orchestrator/graph.py#L675))
   — LLM uniquement pour l'analyse réussie ; tous les autres cas sont des gabarits
   déterministes.

**[C] Coût LLM d'un tour** : de 1 appel (prédiction) à 11 (planificateur + 10
allers-retours SQL), ou 5 pour une analyse (1 + 3 essais + 1 synthèse).

### 1.2 Ce qui est sain

- **[C] Injection de dépendances complète** dans `Orchestrator.__init__`
  ([graph.py:119-135](../src/data_analyst_agent/orchestrator/graph.py#L119)) : modèle,
  catalogue, registre, sandbox. C'est ce qui rend la suite testable sans réseau et
  explique les 97 % de couverture.
- **[C] Nœuds gardés** ([graph.py:234-254](../src/data_analyst_agent/orchestrator/graph.py#L234))
  : une exception renseigne `error` et ne fait pas tomber le graphe.
- **[C] Protocole `DatabaseAdapter`** ([sql.py:166](../src/data_analyst_agent/agents/retrieval/sql.py#L166))
  : Postgres et DuckDB derrière un contrat unique, correctement abstrait.
- **[C] Inférence sans LLM** ([inference/predict.py](../src/data_analyst_agent/agents/inference/predict.py))
  : le calcul est déterministe, le LLM ne fait que rédiger. Le principe est tenu.

### 2.3 Ce que casseraient 10 utilisateurs simultanés — mesuré

**[C] Perte de données, démontrée.** Deux tours concurrents sur la même conversation,
avec 50 ms entre lecture et écriture (pour simuler la durée d'un appel LLM) :

```
MESSAGES PERSISTES : ['q1', 'a1']
ATTENDU : q1, a1, q2, a2 (4 messages) -> 2 messages
```

Cause : `record_turn` fait un lecture-modification-écriture non atomique
([conversations.py:146-165](../src/data_analyst_agent/orchestrator/conversations.py#L146))
— `load()` puis `append` puis `_save()`, sans verrou ni contrôle de version.

**[C] Écrasement silencieux des tableaux intermédiaires**, même expérience :

```
ARTEFACTS AU MANIFESTE : [('resultat_1', 'resultat_1.csv')]
CSV REELLEMENT ECRITS  : ['resultat_1.csv']
```

Cause : le nom est calculé par `f"resultat_{len(self.artifacts) + 1}"`
([workspace.py:157](../src/data_analyst_agent/orchestrator/workspace.py#L157)) sur un
état lu au début du tour. Deux tours partis du même état écrivent le même fichier ;
le second écrase le premier, et le manifeste ne garde qu'une des deux entrées.

**[C] Aucune isolation entre utilisateurs.** `GET /conversations` liste tout
([api/app.py:89-91](../src/data_analyst_agent/api/app.py#L89)), `GET
/conversations/{id}` lit n'importe quel fil, `DELETE` en supprime n'importe lequel,
et `POST /chat` honore un `conversation_id` fourni par le client
([conversations.py:137-144](../src/data_analyst_agent/orchestrator/conversations.py#L137)).
Aucun middleware, aucune dépendance globale — vérifié en instanciant l'application :
`middlewares : (aucun)`, `dependances globales : (aucune)`.

**[C] Le LLM mutualisé, tel qu'il est configuré à la date de cet audit, sert une
requête à la fois** — parallélisme fixé à 1, file d'attente de 512, fenêtre de
32 768 (relevé sur le conteneur en service). Dix utilisateurs posant chacun une
question « query » émettent jusqu'à 110 appels LLM, tous sérialisés sur un unique
créneau. *(Levé depuis : cf. [concurrence.md](concurrence.md).)*

**[C] Pas de budget de temps par requête.** Le client HTTP du provider a
`Timeout(connect=5, read=600, write=600, pool=600)` et `max_retries=2` : un appel LLM
bloqué peut retenir un thread de travail jusqu'à ~30 minutes. Le pool par défaut de
FastAPI pour les endpoints `def` fait 40 threads (mesuré :
`current_default_thread_limiter().total_tokens = 40`) — soit 40 requêtes en vol avant
saturation, sans aucun contrôle d'admission.

**[C] Fuite d'engines Postgres.** `open_source()` est appelée à chaque exécution de
nœud ([graph.py:469](../src/data_analyst_agent/orchestrator/graph.py#L469),
[graph.py:517](../src/data_analyst_agent/orchestrator/graph.py#L517),
[graph.py:600](../src/data_analyst_agent/orchestrator/graph.py#L600)) et fabrique un
`create_engine(dsn)` neuf ([sql.py:188](../src/data_analyst_agent/agents/retrieval/sql.py#L188)),
donc un pool de connexions neuf, **jamais `dispose()`** — `grep dispose src/` ne
trouve rien, alors que `scripts/seed_titanic_postgres.py:85,130` le fait
correctement. Idem pour les connexions DuckDB, jamais fermées. Sous charge, le
`max_connections` de Postgres se remplit.

**[C] Sandbox non plafonnée.** Chaque analyse crée sa propre session
([analysis/agent.py:116-120](../src/data_analyst_agent/agents/analysis/agent.py#L116))
donc un conteneur à `--memory=1g` ([client.py:54-78](../src/data_analyst_agent/sandbox/client.py#L54)).
Dix analyses simultanées = 10 conteneurs et 10 Go réservés, sans file d'attente ni
sémaphore.

**[C] Ce qui, en revanche, ne casse pas** : `Agent.run_sync` fonctionne bien depuis
des threads de travail — testé avec 10 threads concurrents sur pydantic-ai 2.22.0,
10 succès, aucune erreur « event loop is already running ». Le commentaire
d'avertissement du `pyproject.toml` ne concerne que la fixture Playwright de session.

## 3. Mémoire conversationnelle

### 3.1 Où elle vit

Trois objets, tous dans le **même dossier** `workspace_dir/<id>/` :

| Fichier | Écrit par | Contenu |
|---|---|---|
| `transcript.json` | `ConversationStore._save` ([conversations.py:129](../src/data_analyst_agent/orchestrator/conversations.py#L129)) | Le fil affichable : messages, artefacts, `pending`, titre, horodatages. |
| `context.json` | `ConversationWorkspace.record_turn` ([workspace.py:90](../src/data_analyst_agent/orchestrator/workspace.py#L90)) | Le **dernier tour uniquement**. |
| `manifest.json` + `resultat_N.csv` | `save_table` ([workspace.py:154](../src/data_analyst_agent/orchestrator/workspace.py#L154)) | Les tableaux intermédiaires. |

### 3.2 Survit-elle à un redémarrage ?

**[C] Oui, structurellement** : tout est relu du disque à chaque tour
([workspace.py:71-74](../src/data_analyst_agent/orchestrator/workspace.py#L71),
[conversations.py:94](../src/data_analyst_agent/orchestrator/conversations.py#L94)).
Rien n'est gardé en RAM entre deux requêtes — c'est un bon choix, il rendra le
passage multi-instances possible.

**[C] Non, en pratique, avec les réglages par défaut** : `/tmp` est purgé à 10 jours
sur cette machine (§2.2). Et une transcription corrompue est traitée en renvoyant
`None` ([conversations.py:103-110](../src/data_analyst_agent/orchestrator/conversations.py#L103))
— le fil disparaît alors simplement de la barre latérale, sans trace ni alerte.

### 3.3 Ce dont l'agent se souvient vraiment

Beaucoup moins que ce que la persistance suggère :

- **[C] Le transcript n'est jamais renvoyé au LLM.** Aucun appel ne le lit hormis
  l'affichage. Ce qui remonte au planificateur, c'est `describe_context()`
  ([workspace.py:111-123](../src/data_analyst_agent/orchestrator/workspace.py#L111)),
  bâti sur `ConversationContext`.
- **[C] `ConversationContext` ne retient qu'un seul tour** :
  `record_turn` **construit un objet neuf** à chaque tour
  ([workspace.py:101-108](../src/data_analyst_agent/orchestrator/workspace.py#L101)),
  il n'accumule pas. Deux tours en arrière est déjà oublié. La limite est d'ailleurs
  reconnue dans ARCHITECTURE §8, mais son ampleur exacte (un tour, pas « le
  slot-filling ») ne l'est pas.
- **[C] L'agent SQL, sur `main`, ne reçoit aucun contexte** :
  `run_retrieval` ([retrieval/agent.py:123-147](../src/data_analyst_agent/agents/retrieval/agent.py#L123))
  ne prend que la question. C'est précisément ce que corrige Maxizoo (§7).
- **[C] La mémoire utile est donc** : le dernier tour (question, capacité, source,
  code), les features de la dernière prédiction réussie, et la liste de *tous* les
  tableaux intermédiaires.

### 3.4 Comment elle grandit — mesuré

Un objet par tour de type `query`, sans plafond. Mesure sur 30 tours :

```
tour  1:  1 objets | describe() =  619 caracteres (~154 tokens) |  1 montages sandbox |  1 sources ephemeres
tour  5:  5 objets | describe() = 1247 caracteres (~311 tokens) |  5 montages sandbox |  5 sources ephemeres
tour 10: 10 objets | describe() = 2035 caracteres (~508 tokens) | 10 montages sandbox | 10 sources ephemeres
tour 20: 20 objets | describe() = 3625 caracteres (~906 tokens) | 20 montages sandbox | 20 sources ephemeres
tour 30: 30 objets | describe() = 5215 caracteres (~1303 tokens) | 30 montages sandbox | 30 sources ephemeres
```

Croissance **linéaire, ~160 caractères par tour**, sur trois axes simultanés
([graph.py:359-363](../src/data_analyst_agent/orchestrator/graph.py#L359) pour le
prompt du planificateur, [graph.py:490-505](../src/data_analyst_agent/orchestrator/graph.py#L490)
pour les montages sandbox, [graph.py:257-262](../src/data_analyst_agent/orchestrator/graph.py#L257)
pour le catalogue effectif). **Aucun plafond, aucune purge, aucune éviction** dans
`workspace.py`. À 100 tours, le planificateur reçoit ~4 300 tokens de catalogue
d'objets intermédiaires, et le `docker run` de l'analyse porte 100 arguments
`--volume`.

### 3.5 Que se passe-t-il au dépassement de la fenêtre de contexte — mesuré

C'est le point le plus grave de cet axe, et il est **silencieux**. Test contre le
serveur réel (un modèle qui déclare une fenêtre de 131 072, servi avec une fenêtre
effective de 32 768) :

```
caracteres envoyes : 538993 (~134748 tokens estimes)
prompt_eval_count  : 32767
reponse            : Je
erreur             : None
```

Un prompt de ~134 000 tokens a été **tronqué à 32 767 tokens sans aucune erreur**, et
la réponse est inexploitable. Le code ne peut pas le voir : rien ne compte les
tokens, `ModelSettings` ne porte que la température
([llm.py:23](../src/data_analyst_agent/llm.py#L23)), et la trace `TraceStep`
([graph.py:57-60](../src/data_analyst_agent/orchestrator/graph.py#L57)) n'enregistre
ni tokens ni troncature. Un utilisateur qui mène une longue conversation verra donc
la qualité s'effondrer sans qu'aucun message ne l'explique.

## 4. Couplage au moteur LLM

> **Section datée, et tenue depuis.** Elle recensait ce qui, dans le code,
> supposait un moteur d'inférence particulier, et ce qu'il faudrait abstraire
> pour en changer. **C'est fait** : le moteur n'est plus nommé nulle part dans le
> code, l'application ne parle que `/v1/chat/completions`, et
> `DAA_LLM_BASE_URL` suffit à désigner le serveur
> ([ARCHITECTURE §4.3](ARCHITECTURE.md#43-llmpy--configpy--llm-mutualisé-et-réglages)).
> Le recensement point par point est retiré : il désignait des lignes qui
> n'existent plus. Ce qui suit est ce que l'audit avait vu juste, et qui vaut
> encore.

### 4.1 Ce qui n'était PAS couplé, et qui a rendu l'abstraction bon marché

- **[C]** Aucune option propriétaire dans le code : ni `num_ctx`, ni `keep_alive`,
  ni `num_thread`. `grep -n "num_ctx|max_tokens|context_window|ModelSettings" src/ tests/`
  ne ramenait que deux lignes de `llm.py`. Le code n'utilisait **aucune** extension
  hors norme OpenAI.
- **[C]** Les prompts sont neutres — aucun gabarit de chat propre à un serveur :
  [plan.py](../src/data_analyst_agent/orchestrator/plan.py),
  [retrieval/agent.py](../src/data_analyst_agent/agents/retrieval/agent.py),
  [analysis/agent.py](../src/data_analyst_agent/agents/analysis/agent.py),
  [graph.py](../src/data_analyst_agent/orchestrator/graph.py).
- **[C]** Le **format du nom de modèle**, lui, est un point de configuration :
  `DAA_LLM_MODEL` est un identifiant de dépôt Hugging Face
  (`google/gemma-4-E4B-it-qat-w4a16-ct`), pas une étiquette locale. C'est de la
  configuration, pas du code — et c'est le seul endroit où le changement s'est vu.

**La leçon générale** : ce qui coûte dans un changement de moteur n'est pas le
code d'appel, c'est le **nom** du moteur là où il a fui — configuration publique,
`.env` d'exploitation, documentation. Une dépendance nommée dans une variable
d'environnement est une dépendance publique, et elle se paie au changement.

### 4.2 Ce que le moteur exige, et qui a été validé depuis

- **Tool calling — le vrai risque, et il l'était. [C]** Le système en dépend en
  **deux** endroits : l'agent SQL a trois tools
  ([retrieval/agent.py](../src/data_analyst_agent/agents/retrieval/agent.py)), et le
  planificateur utilise `output_type=Plan`, que pydantic-ai réalise **par un appel
  d'outil** — visible sans ambiguïté dans le double de test :
  `tool_call("final_result", plan.model_dump())`
  ([tests/helpers/scripted_llm.py](../tests/helpers/scripted_llm.py)). vLLM ne renvoie
  de `tool_calls` structurés que lancé avec
  `--enable-auto-tool-choice --tool-call-parser <analyseur de la famille du modèle>`.
  **Mesuré depuis** : sans ces options, c'est un HTTP 400 — pas le repli silencieux
  que cette section déduisait —, et un analyseur inadapté ne produit **aucune erreur**,
  seulement des appels d'outil qui fuient dans le texte
  ([MOTEUR.md §3.1 et §7.4](MOTEUR.md)).
- **Modèle servi. [C]** Un serveur vLLM sert **un** modèle, fixé au lancement. Le
  défaut du code désignait alors `qwen3-coder:30b`, qui n'a jamais été chargé —
  vérifié : `POST /v1/chat/completions {"model":"qwen3-coder:30b"}` répondait
  `model not found`. **Corrigé depuis** : le défaut désigne le modèle réellement
  servi, et deux tests le tiennent ([test_settings.py](../tests/unit/test_settings.py)).
- **Montée en charge — le gain principal. [C]** vLLM fait du *continuous batching*
  et sert nativement plusieurs requêtes concurrentes, ce qu'exige le cap
  multi-utilisateurs. **Mesuré depuis** ([concurrence.md](concurrence.md)) : huit
  requêtes simultanées pour +47 % de temps sur une seule. Cela ne lève le goulot du
  §2.3 qu'**à condition** que l'application arrête par ailleurs de sérialiser sur son
  propre pool de 40 threads.
- **Mémoire GPU. [S]** vLLM préalloue son cache KV (`--gpu-memory-utilization`, 0,9
  par défaut) au démarrage et ne le libère pas : la VRAM d'une instance est à compter
  comme réservée en permanence. **Mesuré depuis, et pire que prévu** : ce réglage
  n'est pas une borne dure — 15,48 Gio réellement occupés pour 13,66 demandés
  ([MOTEUR.md §7.5](MOTEUR.md#75-la-mémoire-et-ce-que---gpu-memory-utilization-ne-borne-pas)).
- **Dépassement de contexte. [S]** vLLM renvoie une **erreur HTTP 400** quand le
  prompt dépasse `--max-model-len` (§3.5). Le code ne gérait pas ce cas : l'erreur
  serait remontée brute à l'utilisateur via `_guarded`. Le plafonnement de la
  mémoire (§3.4) était donc un **prérequis**, et non une amélioration indépendante.
  **Traité** : `is_context_refusal()` reconnaît le refus et le dit en clair.

## 6. Sécurité

### 6.1 Exécution du SQL généré — **le trou le plus grave** [C]

Le garde-fou lecture seule ([sql.py:147-160](../src/data_analyst_agent/agents/retrieval/sql.py#L147))
vérifie la forme de la requête (une seule instruction, `SELECT`/`WITH`, mots-clés
d'écriture bannis). Il ne vérifie **pas** ce que le moteur autorise à l'intérieur d'un
`SELECT`. Or DuckDB tourne **dans le process de l'API**, pas dans la sandbox. Résultat
mesuré :

```
[EXECUTE] SELECT * FROM read_csv_auto('/etc/passwd') LIMIT 3 -> ['root:x:0:0:root:/root:/bin/bash'] ...
[EXECUTE] SELECT content FROM read_text('/etc/hostname')     -> [['l4-...-poc-ai\n']]
[EXECUTE] SELECT * FROM glob('/home/ubuntu/*')               -> [['/home/ubuntu/.bash_history'], ...]
```

N'importe quel fichier lisible par l'utilisateur du serveur peut être exfiltré par une
requête générée par le LLM, et le contenu remonte à l'utilisateur comme un tableau de
résultats normal. Le durcissement de la sandbox (§6.2) ne protège rien ici : ce chemin
ne passe pas par la sandbox.

**[C] Le correctif est simple et vérifié.** Le verrou natif de DuckDB
(`SET enable_external_access=false`) ferme l'accès, à condition d'être posé **après**
avoir matérialisé les données :

| Variante testée | Requête légitime | `read_csv_auto('/etc/passwd')` |
|---|---|---|
| `CREATE VIEW` puis verrou | **cassée** (`PermissionException` sur `sources/iris.csv`) | refusée |
| `CREATE TABLE ... AS` puis verrou | **OK** (`SELECT count(*) FROM iris` → 150) | refusée |
| base `.duckdb` en `read_only=True` puis verrou | **OK** (`SELECT count(*) FROM t` → 1) | refusée |

La troisième ligne est le cas Maxizoo, et elle fonctionne : le verrou peut donc être
posé sans rien changer d'autre pour une source de type base DuckDB. La première ligne
impose en revanche de remplacer le `CREATE VIEW` de
[duckdb_excel.py:47-48](../src/data_analyst_agent/agents/retrieval/duckdb_excel.py#L47)
par un `CREATE TABLE ... AS` — ce qui change aussi le comportement mémoire pour un
gros CSV, et doit être arbitré.

### 6.2 Isolation de la sandbox — solide [C]

`docker_run_command` ([client.py:54-78](../src/data_analyst_agent/sandbox/client.py#L54))
applique effectivement ce que la documentation annonce : `--network=none`,
`--read-only` + `--tmpfs=/tmp`, `--cap-drop=ALL`, `--security-opt=no-new-privileges`,
`--memory` avec `--memory-swap` égal (donc pas d'échappement par le swap),
`--pids-limit`, `--rm`, et les montages en `:ro`. Le timeout est à deux étages (bridge
puis hôte). C'est du bon travail.

Deux réserves :
- **[C]** Pas de `--user` au run, contrairement au commentaire du Dockerfile (§1.4) :
  l'isolation repose uniquement sur le `USER 1000:1000` de l'image, qu'un
  `DAA_SANDBOX_IMAGE` mal choisi suffit à annuler.
- **[C]** Les montages sont en lecture seule, mais l'**hôte** écrit dans ces chemins :
  `save_table` ([workspace.py:154](../src/data_analyst_agent/orchestrator/workspace.py#L154))
  et les CSV matérialisés. Le conteneur ne peut pas les altérer — la propriété tient.

### 6.3 Surface exposée par l'API [C]

Vérifié par instanciation de l'application :

```
GET,HEAD  /openapi.json      GET  /health              GET  /conversations/{id}
GET,HEAD  /docs              POST /chat                POST /conversations/{id}/duplicate
GET,HEAD  /redoc             GET  /conversations       DELETE /conversations/{id}
GET,HEAD  /docs/oauth2-redirect                        GET  /
middlewares : (aucun) · dependances globales : (aucune)
```

- **Aucune authentification, aucune autorisation, aucune limitation de débit** sur

- **[C]** Quatre routes non documentées (README §API/Endpoints en liste six) :
  `/docs`, `/redoc`, `/docs/oauth2-redirect`, `/openapi.json` — dont trois chargent
  des assets CDN (§1.4), en contradiction avec la contrainte réseau coupé.
- **[C]** `POST /chat` prend un `message` de longueur non bornée
  ([api/app.py:32-35](../src/data_analyst_agent/api/app.py#L32)) et déclenche jusqu'à
  11 appels LLM et un conteneur Docker : c'est un amplificateur de charge gratuit,

- **[C] Pas de traversée de répertoire** : `safe_dir_name`
  ([workspace.py:55-62](../src/data_analyst_agent/orchestrator/workspace.py#L55))
  réduit tout caractère hors `[0-9A-Za-z_-]` à `_`, donc `../../etc` devient `_etc`.

### 6.4 Gestion des secrets [C]

- Le mot de passe Postgres arrive par `${DAA_PG_PASSWORD}` dans
  `sources/catalogue.yaml:10`, résolu par `os.path.expandvars`
  ([catalog.py:30-42](../src/data_analyst_agent/agents/retrieval/catalog.py#L30)).
  `.env` est bien dans `.gitignore`, et `.env.example` ne contient que `change-me`.
- **Le mot de passe est publié dans `os.environ` du process** par `export_env_file`

  plutôt que par intention.
- Aucun secret d'authentification à gérer côté LLM aujourd'hui (`api_key` factice,
  §4.1) — cela changera avec vLLM.

### Justification de l'ordre

Les tâches 1 à 3 passent devant tout : ce sont trois correctifs de moins d'une
demi-journée chacun qui ferment une exfiltration de fichiers, réparent une CI
actuellement rouge et arrêtent d'écrire les données des utilisateurs dans un dossier
purgé et lisible par tous — les faire plus tard, c'est les faire sur une base plus
large.

Vient ensuite le bloc 4-5-6, qui est le cap multi-utilisateurs proprement dit : la
concurrence d'écriture (4) doit être réglée **avant** l'identité (5), parce
qu'ajouter des utilisateurs sans corriger le lecture-modification-écriture ne fait que
multiplier les pertes de tours déjà mesurées ; et le plafonnement de la mémoire (6)
précède le changement de moteur parce qu'il en est un prérequis, vLLM rendant une
erreur HTTP là où la troncature passait en silence — un cas que le code ne gère pas.

Le changement de moteur (8-9) arrive donc en troisième position malgré sa place dans
le cap, et pour une bonne raison : le swap de code est d'une ligne (§4.1), le seul
risque réel est le *tool calling*, et il se valide sur un banc d'essai isolé (9) sans
bloquer le reste. Tout ce qui suit — durcissement, découpage, documentation — améliore
la durabilité sans conditionner les trois premiers blocs.
